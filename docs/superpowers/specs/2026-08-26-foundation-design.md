# EpiSignal Foundation Design

**Date:** 2026-08-26  
**Status:** Approved  
**Scope:** First implementation slice

## Purpose

Build the lean, Windows-first foundation for EpiSignal without implementing live source ingestion or AI processing. The result will be a modular monorepo with a responsive public shell, a versioned FastAPI service, a hosted Supabase PostgreSQL/PostGIS schema, deterministic seed data, and repeatable quality checks.

The foundation protects the product's central rule: epidemiological facts remain inspectable through their source evidence. Its schema therefore separates sources, signals, events, and observations from the beginning.

## Goals

- Establish a Git monorepo with clear application and package boundaries.
- Run Next.js and FastAPI directly on Windows using the installed pnpm and uv runtimes.
- Use the existing hosted Supabase project for PostgreSQL and PostGIS so Docker is not required.
- Create the complete Phase 1 core schema and canonical disease seed data.
- Provide liveness, readiness, API version, and OpenAPI endpoints.
- Render a polished, responsive public application shell with an honest empty map state.
- Make setup, migrations, seeding, development, linting, testing, type-checking, and production builds repeatable.
- Keep every privileged database credential outside Git and browser bundles.

## Non-Goals

This slice does not implement:

- WHO DON, ECDC, or other live source connectors;
- AI classification or structured extraction;
- geocoding calls;
- event matching or automatic event creation;
- live map markers or event feeds;
- event search or natural-language query parsing;
- authentication, authorization, or an admin review queue;
- deployment automation;
- patient-level data of any kind.

## Architectural Approach

The project uses a modular polyglot monorepo. JavaScript packages are managed with pnpm, Python packages with uv, and root commands provide a consistent interface to both ecosystems.

The dependency direction is:

```text
Browser
  ↓
Next.js web application
  ↓ HTTP / generated contracts
FastAPI service
  ↓ repository and session interfaces
Shared Python backend package
  ↓ private DATABASE_URL
Supabase PostgreSQL + PostGIS
```

The browser never connects with a privileged database credential. The web application calls FastAPI, and FastAPI composes the shared backend package. Future ingestion workers will reuse the backend package without depending on HTTP or web code.

`apps/api/.env.example` documents server settings and the private Supabase connection contract. `apps/web/.env.local.example` documents the single browser-safe API base URL. Developers copy these to ignored `.env` and `.env.local` files in their respective applications.

### Module Responsibilities

`apps/web` owns presentation, responsive layout, public navigation, API readiness display, and the typed API client. It knows nothing about database sessions or SQLAlchemy models.

`apps/api` owns FastAPI startup, dependency injection, HTTP route versioning, request correlation, serialization, and sanitized error responses. It contains no frontend presentation and does not own schema history.

`packages/backend` owns domain enums, SQLAlchemy models, database sessions, repositories, and schema-independent validation. It remains importable by future worker applications.

`packages/contracts` contains generated TypeScript types derived from FastAPI's OpenAPI document. Generated files are updated through a root command and checked for drift.

`database` owns Alembic configuration, ordered migrations, and idempotent seed operations.

## Database Design

The initial migration creates or verifies PostGIS and creates the following tables:

- `sources`
- `signals`
- `diseases`
- `pathogens`
- `events`
- `event_signals`
- `event_observations`
- `event_locations`

### Identity and Audit Fields

Internal identities use UUID primary keys generated by PostgreSQL. Every mutable record includes `created_at` and `updated_at` timestamps stored in UTC. Events also have a unique stable `public_id` and slug for future public URLs.

### Sources

`sources` stores organization or feed identity, type, geographic ownership, public URLs, credibility tier, official status, language, activation state, and audit timestamps. Source type and credibility values are text columns protected by check constraints.

### Signals

`signals` stores one public report or bulletin. It preserves the source relationship, original and canonical URLs, external identifier, title, limited internally used raw text, short summary, publication and retrieval timestamps, language, content hash, relevance decision, signal type, AI audit fields, processing status, and audit timestamps.

The original URL is required and unique. Canonical URL and content hash receive indexes for duplicate detection. Raw text is an internal extraction input and is not automatically exposed through the public API.

### Diseases and Pathogens

`diseases` and `pathogens` provide controlled canonical identities with unique slugs and synonym arrays. Diseases may carry ICD-10 and category metadata; pathogens may carry taxonomy metadata. Events reference these tables instead of storing uncontrolled disease names.

### Events

`events` represents a real-world epidemiological occurrence. It stores public identity, title, disease and pathogen references, event type, operational and verification status, convenient primary geography, PostGIS geography point, important dates, transparent attention and confidence values, evidence-aware summary text, and audit timestamps.

The convenient country and coordinate fields support common list and map queries. Role-specific geography remains authoritative in `event_locations`.

### Event-Signal Relationships

`event_signals` is a many-to-many relationship with relationship type, match score, primary-evidence flag, and creation timestamp. Its composite primary key prevents duplicate links.

### Observations

`event_observations` is append-only application data. Every observation references both its event and the signal that reported it. It stores observation and report dates, suspected, probable, confirmed, total and new cases, deaths, new deaths, recoveries, hospitalizations, CFR, affected-area count, notes, extraction confidence, and creation timestamp.

Updates never overwrite older epidemiological values. Conflicting values from trustworthy reports remain separate traceable observations.

### Locations

`event_locations` stores role-aware geography for primary, exposure, diagnosis, travel, reporting, and affected-area locations. It includes country and administrative names, place name, coordinates, PostGIS geography, geocoding source and confidence, and creation timestamp.

An imported case can therefore represent exposure and diagnosis countries separately.

### Constraints and Indexes

- Status and classification vocabularies use text check constraints rather than native PostgreSQL enums so they can evolve through ordinary migrations.
- Scores and confidence values are constrained to their valid ranges.
- Counts are non-negative when present.
- CFR is non-negative when present; it is not silently recomputed when the source reports a value.
- Foreign keys protect provenance relationships.
- Canonical slugs and source URLs use uniqueness constraints.
- Event status, verification, disease, country, and update time receive targeted indexes.
- Signal source, publication time, processing status, canonical URL, and content hash receive targeted indexes.
- Observation event and observation date receive a compound index.
- Geography columns receive GiST indexes for later distance and bounding-box queries.
- The schema contains no patient names, precise residential addresses, contact data, or other patient-level structures.

## Seed Design

The initial disease vocabulary comes from the Phase 1 specification and includes canonical names, stable slugs, common synonyms, and categories where known. Initial source records describe WHO Disease Outbreak News and ECDC as inactive connector definitions until their later ingestion slice is implemented.

The seed command uses stable natural keys and PostgreSQL upserts. Running it repeatedly updates canonical metadata and produces no duplicate diseases or sources. It does not delete locally added records.

## Configuration and Supabase Connection

The repository commits `apps/api/.env.example` and `apps/web/.env.local.example` but ignores `apps/api/.env`, `apps/web/.env.local`, and all environment-specific secret files.

The API configuration contract includes:

- `EPISIGNAL_ENV`
- `EPISIGNAL_API_HOST`
- `EPISIGNAL_API_PORT`
- `EPISIGNAL_DATABASE_URL`
- `EPISIGNAL_CORS_ORIGINS`
- `EPISIGNAL_LOG_LEVEL`

The web configuration contract includes only:

- `NEXT_PUBLIC_EPISIGNAL_API_URL`

The Supabase connection string is normalized to the SQLAlchemy psycopg driver format inside the API process. It is never printed in full, returned from an endpoint, embedded in generated OpenAPI, or exposed to Next.js client code.

Setup documentation instructs the developer to enable PostGIS in the existing Supabase development project, copy the appropriate connection string, URL-encode special password characters when needed, create ignored local environment files, run the migration preflight, apply migrations, and seed canonical data.

Application startup never applies migrations automatically.

## Public API Foundation

The FastAPI service exposes:

```text
GET /health/live
GET /health/ready
GET /api/v1
GET /openapi.json
GET /docs
```

`/health/live` confirms that the process can serve requests and performs no database call.

`/health/ready` performs a bounded database query and verifies the PostGIS extension. A ready response contains component states without credentials or host details. A failed check returns HTTP 503 with a stable machine-readable error code.

`/api/v1` returns API name and semantic version metadata. Event read endpoints arrive in the ingestion vertical slice, after real event records exist.

## Error Handling and Logging

Missing or invalid configuration fails at process startup with the setting name and corrective guidance. Error messages never include setting values.

Every HTTP request receives or propagates an `X-Request-ID`. Unexpected failures are logged with that identifier and returned as sanitized JSON. Expected readiness failures use explicit response models and HTTP 503. Validation errors retain FastAPI's structured field information without leaking internal state.

Database operations use short bounded connection timeouts. The API does not retry migrations or writes implicitly. Migration and seed commands exit non-zero with an actionable phase label while preserving the original exception in developer-facing terminal output.

## Web Shell Design

The public shell establishes EpiSignal's design language:

- warm off-white background;
- deep navy structure and typography;
- restrained teal for trusted system states;
- editorial headline typography paired with a highly readable interface sans serif;
- generous whitespace and strong contrast;
- semantic HTML, keyboard-visible focus, and non-color status labels.

Desktop layout includes a compact masthead, product statement, prominent search-shaped preview, global-map placeholder, and system-readiness panel. The search control is visibly marked as unavailable until event search exists; it does not pretend to execute a query.

Mobile layout preserves the map context and introduces the bottom-sheet structure intended for event discovery. The sheet shows foundation readiness rather than fabricated outbreak data.

The shell calls the API readiness endpoint through a typed server-side client. It renders distinct loading, connected, and unavailable states. A database outage does not prevent the page shell from rendering.

No severity color, event statistic, source count, or outbreak claim appears before real evidence exists.

## Development Commands

Root commands provide stable entry points for:

- dependency setup;
- web and API development processes;
- database preflight, migration, rollback, and seeding;
- OpenAPI contract generation and drift checking;
- formatting and linting;
- Python and TypeScript type-checking;
- backend and frontend tests;
- complete verification;
- production builds.

PowerShell-compatible commands are documented first because the initial environment is Windows. The underlying pnpm and uv commands remain cross-platform.

## Testing Strategy

Implementation follows test-driven development for behavior-bearing code.

Backend unit tests cover safe configuration parsing, URL normalization, domain constraints, seed payload stability, request identifiers, liveness, readiness success, and readiness failure. Database dependencies are injected so health behavior can be tested without Supabase credentials.

Migration tests inspect revision metadata and schema declarations without touching an unknown hosted database. After the developer configures the Supabase development project, an explicit live smoke command applies migrations, verifies expected tables and PostGIS, runs seeds twice, and checks idempotency. The live command is never part of an automatic unit-test run.

Frontend tests cover the public shell, accessible landmarks, disabled search preview, readiness states, and mobile bottom-sheet structure. Production verification also runs linting, type-checking, contract drift checking, and a Next.js build.

## Acceptance Criteria

The foundation is complete when:

1. `pnpm install` and `uv sync` succeed using the documented supported runtimes.
2. Formatting, linting, Python and TypeScript type-checking, unit tests, contract checking, and production builds pass from root commands.
3. No unit test requires Docker, Supabase credentials, or network access.
4. With a configured Supabase development URL, the preflight confirms connectivity and PostGIS availability.
5. Alembic upgrades an empty target schema to the complete Phase 1 core model.
6. Running seeds twice produces the same canonical disease and source identities without duplicates.
7. FastAPI exposes liveness, readiness, version metadata, OpenAPI, and interactive documentation.
8. Readiness returns structured HTTP 503 when the database is unavailable.
9. Next.js renders the responsive EpiSignal shell and displays API readiness without exposing the database URL.
10. The browser receives no fabricated event or epidemiological data.
11. Secret environment files, caches, build outputs, and brainstorming artifacts are excluded from Git.
12. The README enables a Windows developer with Node.js, pnpm, Python, uv, and an existing Supabase project to reach a running web and API foundation.

## Follow-On Slice

After this foundation, the next independent design and implementation cycle will build the first evidence-to-event vertical slice: a WHO DON connector, persisted signals, strict extraction fixtures and schemas, geocoding boundary, conservative event creation, observation creation, event read APIs, and live map records.
